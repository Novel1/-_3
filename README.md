# Кейс-задача №3 — прототип экспертной системы (консультант Sulpak по подбору смартфона)

## Запуск

```bash
cd case3_expert_system
python gui.py          # графический интерфейс (Tkinter, входит в стандартный Python). Запуск от сюда
python test_engine.py  # прогон 5 тестовых сценариев без GUI — проверка логики
```

Зависимостей, кроме стандартной библиотеки Python 3, не требуется.

## Файлы

| Файл | Назначение |
|---|---|
| `engine.py` | Универсальный движок вывода с прямым (forward chaining) выводом — самописная лёгкая "оболочка" экспертной системы: рабочая память фактов + правила «ЕСЛИ…ТО…» + журнал рассуждений. |
| `knowledge_base.py` | База знаний: вопросы к пользователю и ~40 правил в 3 уровня вывода. |
| `gui.py` | Графический интерфейс-опросник на Tkinter, показывает результат и объяснение хода рассуждений. |
| `test_engine.py` | 5 тестовых сценариев для проверки корректности вывода. |

## Обзор существующих оболочек экспертных систем и обоснование выбора

Изучены классические оболочки, упомянутые в задании:

| Оболочка | Особенности | Почему не использована в прототипе |
|---|---|---|
| **CLIPS** | Промышленный стандарт, C-подобный Lisp-синтаксис, мощный forward/backward chaining | Требует установки отдельного рантайма и изучения собственного языка правил — избыточно для учебного прототипа |
| **Jess** | Java-реализация CLIPS, интеграция с Java-приложениями | Требует JVM и лицензирования (коммерческая для бизнеса) |
| **EMYCIN** | Один из первых shell'ов (на основе MYCIN), для медицинской диагностики с уверенностью (certainty factors) | Устарел, нет актуальной реализации |
| **FirstClass** | Коммерческая ЭС-оболочка для бизнес-правил | Проприетарная, недоступна для учебных целей |
| **GURU** | Коммерческая ЭС с интеграцией с БД/Excel | Проприетарная, платная |

**Вывод:** для учебного прототипа выбрана собственная минимальная оболочка на
Python — она реализует те же базовые принципы экспертной системы (факты,
продукционные правила, машина вывода, объяснение), но не требует установки
дополнительного ПО, полностью прозрачна (весь код виден и объясним на защите)
и легко переносится/расширяется. Это соответствует духу задания: изучить
*принципы* построения экспертных систем, а не освоить синтаксис конкретного
коммерческого продукта.

## Архитектура (соответствие шагам алгоритма кейс-задачи)

1. **Предметная область** — подбор категории и линейки смартфона для
   покупателя магазина Sulpak (розница электроники — прямое применение
   к месту практики).
2. **Анализ существующих решений** — таблица выше.
3. **Структура базы знаний** — `knowledge_base.py`: 5 входных фактов
   (бюджет, сценарий использования, бренд, нужен ли 5G, объём памяти),
   ~40 правил в 3 уровня (категория → линейка → уточнения).
4. **Механизм логического вывода** — `engine.py`: прямой вывод (forward
   chaining), правила применяются пока рабочая память не перестанет
   пополняться новыми фактами; ведётся журнал сработавших правил.
5. **Интерфейс пользователя** — `gui.py`: пошаговый опросник (Tkinter),
   по одному вопросу за раз, с возможностью вернуться назад; итог —
   рекомендация + пошаговое объяснение вывода.
6. **Тестирование и отладка** — `test_engine.py`: 5 сценариев
   (в т.ч. с неполными входными данными), все проходят (5/5, exit code 0).
7. **Документирование** — этот файл + раздел 4 отчёта по практике.
